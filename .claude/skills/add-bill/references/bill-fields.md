# 본문 필드 규칙 (`src/types/bill.ts`의 `Bill`)

타입 정의는 [`src/types/bill.ts`](../../../../src/types/bill.ts)에 있다. 여기는 **무엇을 넣을지**를 적는다.

## 0. 머리 정보

| 필드 | 규칙 |
|---|---|
| `slug` | 영문 소문자-하이픈-연도. 파일명·URL·개인화 레이어가 모두 이 값을 쓴다. **나중에 바꾸지 않는다.** |
| `title` | 정식 법안명. 상세 페이지에서 보조 정보로 작게 나온다. `국민연금법 개정안 — 18년 만의 …`처럼 부제를 붙여도 된다 |
| `shortTitle` | 카드·목차·매트릭스에 쓰는 짧은 이름. **12자 안팎.** 매트릭스 행 이름이라 길면 표가 깨진다 |
| `category` | **문자열 하나.** 아래 참고 |
| `tags` | 검색어. 아래 참고 |
| `status` | 7종 중 하나. 아래 참고 |
| `proposedDate` `passedDate` `promulgatedDate` `effectiveDate` | `YYYY-MM-DD`. 해당 단계를 지났을 때만 넣는다 |
| `lastUpdated` | 이 문서를 마지막으로 손본 날. 비개인화 목록의 정렬 키다 |

### `category` — 필터 칩이 되는 값

목록 화면의 `분야` 필터는 데이터에서 자동으로 만들어진다(`getAllCategories()`).
값 하나가 칩 하나다. **새 값을 만들면 칩이 하나 늘어난다.**

현재 쓰이는 값:

```
복지·연금   노동   세제   사법   정치개혁
```

새 분야를 만들 기준: 앞으로 **2건 이상**이 들어올 영역인가? 한 건뿐이면 기존 값 중
가장 가까운 것에 넣는다. 칩이 한 건짜리로 늘어나면 필터가 쓸모없어진다.
가운뎃점(`·`)으로 두 낱말을 묶는 기존 표기를 따른다 (`복지·연금`).

### `tags` — 검색어

필터가 되지 않는다. `title` `shortTitle` `category` `summary30s`와 함께 검색 대상 문자열로
합쳐질 뿐이다. 카드에는 앞의 3개만 보이고 나머지는 `외 N개`로 접힌다.

넣을 것: 법 이름, 별칭, 핵심 쟁점, 사람들이 검색창에 실제로 칠 말.

```ts
tags: ["국민연금", "연금개혁", "보험료율", "소득대체율"]
tags: ["노동조합법", "손해배상", "하청노동자", "노란봉투법"]  // 별칭이 검색어로 중요
```

넣지 말 것: 정당명, 의원 이름, `심사중` 같은 상태값(이미 필터가 있다), 감정어.

**중요한 별칭은 앞쪽에 둔다.** 카드에 3개까지만 보이기 때문이다.

### `status` — 7종과 짝이 되는 날짜

| `status` | 뜻 | 있어야 하는 날짜 |
|---|---|---|
| `발의` | 국회에 제출됨 | `proposedDate` |
| `심사중` | 상임위 심사 | `proposedDate` |
| `본회의_계류` | 위원회 통과, 본회의 대기 | `proposedDate` |
| `통과` | 본회의 통과, **시행 전** | `passedDate` |
| `공포` | 공포됨, **시행 전** | `passedDate` `promulgatedDate` (+ 정해졌으면 `effectiveDate`) |
| `시행` | 효력 발생 | `effectiveDate` |
| `폐기` | 임기만료·부결 | — |

개인화 문구의 시제가 이 값에서 **자동으로** 나온다(`src/lib/impact/status.ts`).
`공포`인데 실수로 `시행`이라고 쓰면 "현재 적용되고 있습니다"라고 잘못 서술된다.

`시행`인데 `effectiveDate`가 미래면 시스템이 알아서 "시행일 전까지는 적용되지 않습니다"로
바꿔 쓴다. 이건 손으로 처리하지 않아도 된다.

## `claimType` — 이 프로젝트의 핵심

거의 모든 구조에 `claimType`이 붙는다. **감으로 붙이지 말고 이 순서로 판단한다.**

```
원자료(법 조문·정부 통계)에서 그대로 확인되는가?
  예 → fact
  아니오 ↓
누군가가 공식적으로 밝힌 입장인가? (그 말이 맞는지와 무관하게)
  예 → official_claim
  아니오 ↓
아직 일어나지 않은 일에 대한 예상인가?
  예 → forecast
  아니오 ↓
확인된 사실들을 엮은 분석·해석인가?
  예 → interpretation
  아니오 ↓
제기됐지만 사실로 확인되지 않았는가?
  예 → allegation
```

자주 틀리는 경계:

- "정부 추계로는 기금 소진이 2064년" → **`forecast`**. 정부가 말했다는 사실은 확인되지만
  내용 자체가 미래 예측이다. `official_claim`이 아니다.
- "복지부는 저부담-저급여로는 보장이 어렵다고 본다" → **`official_claim`**. 입장 표명이다.
- "소득대체율 상향은 저소득층에게 비례적으로 유리하다" → **`interpretation`**.
  일반 원리에서 끌어낸 분석이다.
- "2025년 3월 20일 본회의를 통과했다" → **`fact`**.

## 10단계 본문

### ① `summary30s` — 30초 요약

한 문단. **결론부터.** 무엇이 어떻게 바뀌는지 → 언제 → 무엇이 빠졌는지 순으로.
상세 페이지 본문 첫 블록이자 카드 요약(3줄로 잘림)이자 메타 설명(155자로 잘림)이다.
**앞 155자 안에 핵심이 들어가게 쓴다.**

### ② `comparison` / `comparisonNote`

`{ aspect, before, after, note? }`의 배열. 3~5개.

- `aspect`는 짧은 명사구 (`보험료율`, `최고세율`, `공제 구조`)
- `before`는 **현행 제도**. "없음"이 답이면 `제도 없음`이라고 명시한다
- `note`는 표만 보면 오해할 수 있는 것을 잡는다. 예: "직장가입자는 절반씩 부담하므로 개인 부담은 …"
- `comparisonNote`는 **표에서 뺀 것과 그 이유**를 적는 자리다.
  "수급개시연령 조정은 2007년 개정으로 이미 확정된 스케줄이라 제외했다"

### ③④ `proponentArguments` / `opponentArguments`

`{ point, detail, claimType, attribution, source? }`의 배열. 각 2~3개.

- **양쪽에서 가장 센 논리를 고른다.** 반박하기 쉬운 약한 주장을 골라 넣는 것이
  이 섹션에서 가장 하기 쉬운 실수다.
- `attribution`은 주체. 정당명 대신 역할로 적는다: `경영계(경총·대한상의 등)`,
  `청년 세대 비판 여론`, `조세 형평성 관점의 비판적 시각`
- `point`는 그쪽 입장에서 쓴 한 문장. `detail`은 근거와 맥락.

### ⑤ `mechanismSummary` / `mechanismSteps`

법이 실제로 어떻게 작동하는지. `mechanismSteps`는 `{ step, detail }`의 **시간 순서**
배열이고 화면에서 세로선으로 이어진다. 3~4단계.

"무엇이 자동으로 일어나고, 무엇이 누군가의 판단에 달렸는지"를 구분해 적으면 좋다.
판단에 달린 부분이 대개 개인화 레이어의 `uncertainties`가 된다.

### ⑥ `beneficiaries` / `costBearers` / `fiscalImpact` / `sideEffectRisks`

`{ who, how, scale?, claimType, source?, pathwayId? }`의 배열.

- `who`는 집단 이름. `2030~2040세대 가입자`, `하청·특수고용 노동자`
- `how`는 **어떤 경로로** 이득·부담이 생기는지
- `scale`은 있을 때만. 단위와 기준을 함께: `월 소득 300만원 기준 약 13.5만원→19.5만원(2033년, 세전)`
- **`pathwayId`는 개인화 경로와 연결하는 고리다.** 대응하는 `ImpactPathway.id`를 적으면
  자유문장 요약과 구조 데이터가 어긋나는 것을 검증 스크립트가 잡아 준다.
  방향(`benefit`/`burden`)이 확정된 경로는 여기 연결되지 않으면 경고가 뜬다.

`sideEffectRisks`는 **의도하지 않은 결과**만. 반대 측 주장을 여기 옮기지 않는다(③④에 있다).

### ⑦ `evidence` / `uncertainties`

`evidence`는 `{ text, claimType, certainty, source? }`. `certainty`는 `높음`/`중간`/`낮음`
3단이고 화면에서 막대로 그려진다. **이 눈금은 개인화 레이어로 확장하지 않는다** —
개인화는 `evidenceMethod`라는 다른 체계를 쓴다.

`uncertainties`는 문자열 배열. **"무엇을 아직 모르는가"**를 적는 자리다.
"자료가 언제 나오는지"까지 적으면 좋다. 대개 여기 적은 것이
개인화 경로의 `uncertainties`와 겹친다.

### ⑧ `analysisFacts` / `analysisJudgment`

두 배열이 화면에서 좌우로 갈라져 나온다. 섞으면 안 된다.

- `analysisFacts`: 자료로 뒷받침되는 것만
- `analysisJudgment`: **모든 항목을 `[의견]`으로 시작**한다. 관례가 아니라 화면 규칙이다

### ⑨ `predictions`

`{ id, by, date, claim, horizon, fallsifiedBy? }`.

- `id`는 법안 안에서 유일한 짧은 키(`np-1`, `yea-2`). `outcomeTracking`이 참조한다
- `by`는 예측 주체. 입법로그 자신의 예측도 넣는다(`by: "입법로그"`)
- `horizon`은 `6개월` / `1년` / `3년` 중 하나
- **`fallsifiedBy`가 핵심이다.** "무엇을 확인하면 이 예측이 맞았는지 알 수 있는가".
  구체적인 통계·보고서 이름을 적는다. 이걸 못 적으면 그건 검증 불가능한 주장이다

### ⑩ `outcomeTracking`

`{ horizon, checkDate, status, findings, relatedPredictionIds?, source? }`.

- 세 시점(`6개월`/`1년`/`3년`)을 **미리 만들어 둔다.** 아직이면 `status: "추적예정"`과
  언제 무엇을 볼지를 `findings`에 적는다
- 자료는 나왔는데 인과를 정책 하나로 돌리기 어려우면 `판단보류`. **`빗나감`이 아니다**
- 예측을 나중에 고치지 않는다. 채점만 한다

## `sources`

`{ label, publisher, type, date?, url? }`. `type`은
`법령` `법안원문` `공식통계` `연구자료` `보도자료` `언론보도` `국회회의록` `기타`.

- 본문 어딘가에서 쓴 출처는 **전부** 여기 있어야 한다
- 1차 자료(법령·법안원문·공식통계)를 최대한 앞에 둔다
- `url`이 없으면 `publisher`와 `date`가 함께 있어야 나중에 찾을 수 있다
